# Compiler/interpreter optimization opportunities: Luau 0.740 and L3i

Research date: 2026-10-01. Scope: interpreter dispatch, compiler-generated bytecode, source shape, plain tables, calls, and the configuration that selects their fast paths. No production edits or VM patches. Buffer/vector implementations, Rust binder dispatch internals, GC implementation, and template instantiation implementation are deliberately excluded.

## 1. What is actually implemented and configured today?

### Takeaway

L3i already embeds an optimizing Luau compiler and interpreter, with optional native code generation; it is not an established source-to-source engine frontend. The strongest initial opportunity is to make an engine's generated-source contract and loading path explicit, then exploit existing compiler/VM fast paths rather than fork the VM. **Hot-path risk: medium**, rising if the engine executes unsandboxed builtins, indirect micro-calls, dynamic string indexing, or an unintended interpreter-only loading path.

### Cited findings

**Repository/pin evidence.** Commands in this checkout reported L3i HEAD `62b894e3180baeb7bdced72afb4c99a6676951a4`; `git ls-tree HEAD luau` and `git submodule status` both identify `c0e346edd89066b44dca174c9f54ce84c746a540`, tag `0.740`. `git -C luau status --short` and its diff were empty. `PLAN.md` is absent, as the assignment warned; no parity claims below depend on it. The declared version and build source agree with this observation: [build.rs:27–29,88–94](../../build.rs#L27), [Cargo.toml:16–18](../../Cargo.toml#L16).

**Actual product boundary.** The public compilation API accepts a Luau source string and forwards it to `luau_compile`; it does not lower an L3i language/IR into Luau. `syntax` exposes the upstream parser as tables, `analysis` exposes Luau's analysis frontend, and plan-generated `.d.luau` files describe host APIs. Inspection of `src/`, `examples/`, and the project description found no production engine source emitter. This is a bounded negative finding, not a claim about an external engine repository. Native `IrBuilder` hooks are not a source frontend. **Loading paths must not be conflated.** `LoadScope::load_bytecode` invokes the native generator when installed, and `LoadScope::load_source` delegates to it. In contrast, `Runtime::load` and `load_with_env` compile and call `luau_load` without a generator call; `load_function`, `eval`, and `exec` use `Runtime::load`. A host can therefore configure a native runtime yet run code interpreted through those convenience methods. This is an API-path observation, not a proposed change to their contract. The sandbox template path separately applies native compilation. [source.rs:229–269](../../src/source.rs#L229), [runtime/mod.rs:445–495,596–631](../../src/runtime/mod.rs#L445), [sandbox.rs:399–446](../../src/sandbox.rs#L399).

**Safeenv is a performance contract, not just a readonly bit.** `GETIMPORT` copies a pre-resolved constant only if that constant is non-nil and the executing closure's environment is safe; otherwise it resolves the chain again. The loader resolves import constants only when the loading thread's globals are safe. Turning safeenv on *after* loading does not populate those nil import constants. `FASTCALL*` also tests safeenv before skipping the fallback lookup and ordinary CALL. Calling Lua `getfenv` marks the returned environment unsafe; `setfenv` also disables it. At compile time these names inhibit important folding/inlining. [lvmexecute.cpp:489–508,3030–3075](../../luau/VM/src/lvmexecute.cpp#L489), [lvmload.cpp:177–219](../../luau/VM/src/lvmload.cpp#L177), [lbaselib.cpp:128–154](../../luau/VM/src/lbaselib.cpp#L128), [Compiler.cpp:5678–5705](../../luau/Compiler/src/Compiler.cpp#L5678).

L3i exposes two different sandbox strategies: `sandbox_globals()` freezes the real globals and enables safeenv after installation; plan policy invokes it only when requested. The separate `Sandbox` API already builds a safe base environment and loads templates against it, and excludes environment escape hatches. Its default compatibility `pairs`/`ipairs` wrappers honor legacy metamethods; do not erase these semantics in a generated loop rewrite. [runtime/mod.rs:589–594](../../src/runtime/mod.rs#L589), [extension/install.rs:465–481](../../src/extension/install.rs#L465), [sandbox.rs:1–18,35–105,193–214,237–290](../../src/sandbox.rs#L1).

### Inferences

- No new optimization level switch is needed: O2 is already the default. A future emitter should preserve visible local functions, constants, builtin identities, static keys, and ordinary loops so that upstream optimizations can see them.
- Compile/load outside frame updates and retain callable functions. `load_source` and runtime convenience source loaders compile again per call; the explicit `compile`/`load_bytecode` split already permits bytecode reuse. If the engine adds a persistent bytecode cache, its identity must account for source, Luau pin/bytecode format, compiler flags/options, and compiler-known constants/type metadata; hot reload must invalidate folded assumptions. This is an engine cache contract, not a request for new hashing in the invocation path. [source.rs:168–181,241–269](../../src/source.rs#L168), [runtime/mod.rs:445–467,596–631](../../src/runtime/mod.rs#L445).
- Choose an immutable service namespace plus explicit function parameters/local state for generated engine kernels. Do not use mutable global member chains as if they were stable imports; mark mutable roots via `mutable_globals` where necessary. Runtime-known library constants are a promise: once folded, changing the source member cannot be repaired by a later safeenv check. [Compiler.h:61–74](../../luau/Compiler/include/Luau/Compiler.h#L61), [Compiler.cpp:5685–5727](../../luau/Compiler/src/Compiler.cpp#L5685).
- Do not change all L3i runtimes to sandboxed/native by default just for a microbenchmark. Establish the generated-engine profile at the host boundary; handwritten compatibility code may need different behavior.

### Gaps

- No engine emitter, representative generated workload, or engine call-site policy was provided. Candidate “emitter changes” below are contracts/fixtures for a future emitter, not claims about a defective existing compiler pass.
- No end-to-end L3i runtime timing was collected. Static instruction/IR evidence below establishes removed work, not measured percentage gains.

## 2. Which source/configuration changes can eliminate costs without VM patches?

### Takeaway

Ranked for likely return versus implementation risk: (1) correct fast-path environment/loading contract, (2) visible fixed-arity local kernels, (3) semantic loop selection, (4) stable literal table schemas/static keys, and (5) opt-in typed native kernels. All five can use existing APIs and unchanged upstream VM code. The rankings are hypotheses for the engine workload, not a measured league table.

### Cited findings: dispatch, calls, and table model

- **Dispatch already uses computed goto on clang/GCC.** Instructions are one or more 32-bit words, not uniform single-word operations; AUX words are data, not extra dispatches. `SingleStep` takes a different dispatch route. Eliminating emitted operations is a more defensible first target than another dispatch implementation. [lvmexecute.cpp:135–159](../../luau/VM/src/lvmexecute.cpp#L135), [Bytecode.h:11–31](../../luau/Common/include/Luau/Bytecode.h#L11).
- **Scalar arithmetic retains dynamic guards.** ADD checks both operands for number tags before the ordinary numeric path; ADDK takes a numeric constant and checks only the register operand. Nonmatching values take other type/metamethod paths. Keeping true constants visible can remove loads and one dynamic operand check; annotations alone do not remove the interpreter's checks. Do not algebraically reassociate floating-point/effectful operations just to obtain a K opcode. [lvmexecute.cpp:1760–1803,2072–2090](../../luau/VM/src/lvmexecute.cpp#L1760).
- **Ordinary CALL is not a direct machine call just because the source callee is local.** The VM checks function/callable status, establishes a CallInfo/base/top, checks stack space, fills missing parameters, and reenters the Luau code or calls C. Inlining is what removes that machinery. Fixed arity also avoids `PREPVARARGS` parameter relocation. [lvmexecute.cpp:1060–1156,2965–2992](../../luau/VM/src/lvmexecute.cpp#L1060).
- **Builtin calls have a separate path.** At O1+ the compiler recognizes builtins, including tracked immutable local aliases; specialized FASTCALL1/2/2K/3 can avoid argument moves and the ordinary call frame on success. The fallback bytecode remains present and must not be counted as executed fast-path work. [Compiler.cpp:1415–1489,1573–1582](../../luau/Compiler/src/Compiler.cpp#L1415), [Builtins.cpp:18–68](../../luau/Compiler/src/Builtins.cpp#L18), [lvmexecute.cpp:3030–3075,3149–3198](../../luau/VM/src/lvmexecute.cpp#L3030).
- **Tables are split arrays/hash tables, not hidden-class objects.** Positive integral numeric keys can occupy the array; density and boundary rules influence sizing. The hash is chained scatter with Brent's variation, using interned-string hashes. `GETTABLEKS` predicts one node using the opcode's 8-bit C field and `nodemask8`, validates string identity/non-nil value, and patches the instruction on a miss. Stable key sets/order/capacity help but are not a shape-ID guarantee. The cache is a slot hint, not a cached value. [ltable.cpp:4–24,66–69](../../luau/VM/src/ltable.cpp#L4), [lvmexecute.cpp:511–557](../../luau/VM/src/lvmexecute.cpp#L511).
- **Array lookup specializes differently.** `GETTABLE` has a numeric-index fast path with table/number, integral index, bounds, and no-metatable checks. A dynamic string key does not get that path. `GETTABLEN` encodes constant numeric indices 1–256 and avoids index-register conversion/exactness checks; table/bounds/metatable checks remain. Even a harmless metatable excludes these direct array paths. [lvmexecute.cpp:764–879](../../luau/VM/src/lvmexecute.cpp#L764), [Bytecode.h:159–170](../../luau/Common/include/Luau/Bytecode.h#L159).
- **NAMECALL is not simply GETTABLEKS with a receiver.** For a plain table it first probes the full-hash main position; its predicted C slot accelerates an `__index` table, whereas GETTABLEKS uses its predicted slot for the base table. Colliding methods can therefore behave differently. NAMECALL copies receiver/function and normally falls directly into CALL in L3i's flag policy. Non-table receivers can invoke `__namecall`, so lookup-and-call is not universally equivalent. [lvmexecute.cpp:925–1057](../../luau/VM/src/lvmexecute.cpp#L925), [Bytecode.h:176–183](../../luau/Common/include/Luau/Bytecode.h#L176).

### Candidate 1 — Make the engine's immutable environment and hot loading path explicit

**Current behavior/evidence:** Plan safeenv is opt-in; sandbox templates already establish it. The bytecode compiler emits FASTCALL/import optimizations regardless of whether the host later makes their runtime fast path available. Normal runtime convenience loading does not automatically compile native code. See the configuration and loading-path sources in §1.

**Smallest proposed change:** At engine setup, install services before freezing/sandboxing; load generated kernels on that safe thread. Keep generated per-frame state in locals/arguments, prohibit generated `getfenv`/`setfenv`, retain O2/debug1/coverage0, and compile with the runtime-derived options. For native experiments choose `LoadScope::load_source`/`load_bytecode` or the existing template path rather than assuming `Runtime::load_function` applies the policy. No VM change. Keep a deliberately unsafe/mutable profile only as a correctness/benchmark control.

**Instruction/branch/load argument:** Successful GETIMPORT becomes a guarded constant load rather than repeated chained table resolution. Successful FASTCALL jumps past fallback MOVE/GETIMPORT/CALL, avoiding an entire ordinary call frame. This can benefit each inner-loop builtin. The disassembled `math.abs(x)` below has a single FASTCALL1 plus RETURN on its successful path, versus the fallback MOVE, GETIMPORT, CALL sequence as well; it does not mean a FASTCALL is one CPU instruction. Environment changes do not themselves shrink the bytecode, and disabled fast paths still execute their guard. [lvmexecute.cpp:489–508,3149–3198](../../luau/VM/src/lvmexecute.cpp#L489).

**Benchmark:** Compile/load once, then execute loops of 1, 32, 1,024, and 100,000 operations using dynamic inputs. Compare identical math/bit operations and stable service lookups in safe-before-load, unsafe, and safe-after-load controls. Separately time compile/load so it cannot hide the execution gain. Include an engine module loaded through the actual host path, and check native status when applicable.

**Estimated patch size:** 20–60 lines of host setup/policy once its call site is known, plus 100–180 lines of fixtures/benchmarks; zero interpreter binary changes. These are planning estimates, not edits to an existing frontend.

**Risks/confidence:** Low upstream/rebase risk; medium/high semantic risk if the host freezes a namespace that scripts are allowed to mutate or lies about builtin identity. Preserve sandbox compatibility wrappers; do not forcibly turn safeenv back on after arbitrary environment mutation. High confidence in the fast-path mechanism; workload benefit unmeasured. Existing sandbox-template users may already receive essentially all of this benefit.

### Candidate 2 — Emit small fixed-arity local kernels, not dynamic dispatch for every operation

**Current behavior/evidence:** O2 attempts local-function inlining; methods (`expr->self`), variadic functions, recursion, multret requirements, environment access, and cost/depth budgets constrain it. Closure captures distinguish immutable value capture from reference capture. Closure sharing is already attempted, including eligible top-level immutable captures; runtime equality/environment checks may still prevent reuse. [Compiler.cpp:624–653,950–1029,1373–1401,1620–1715](../../luau/Compiler/src/Compiler.cpp#L624), [lvmexecute.cpp:2906–2962](../../luau/VM/src/lvmexecute.cpp#L2906).

**Smallest proposed change:** A generated numeric helper should be a visible `local function helper(x) ... end`, called with a known fixed result count, rather than a table of operation functions, callback parameter, or per-element capturing wrapper. Keep mutable state explicit in arguments where the language contract permits. Preserve builtin identities rather than hiding them in arbitrary callback objects. Let O2 inline before considering manual expansion.

**Instruction/branch/load argument:** The actual test's `helper(x) = x*2+1`, called with `local y=helper(x)`, compiled into `MULK; ADDK; RETURN`, with an “inlining succeeded” remark. `local y=f(x)` retained `MOVE; MOVE; CALL; RETURN` and also executes the callee's arithmetic/return when invoked. The win is removal of frame setup, call dispatch, return work and argument copies—not merely substituting one local variable. Blindly emitting larger inlined bodies can instead inflate bytecode/I-cache pressure. Compiler sharing already prevents many capture-free closure allocations; do not count every `function` expression as an allocation.

**NAMECALL/caching qualification:** For actual methods, preserve `obj:method(...)` unless the receiver is a proven plain table and early binding is intended. The test colon call uses one fewer MOVE/word than `obj.method(obj, ...)`, and benefits from NAMECALL-to-CALL fallthrough. For a stable plain-table method in a loop, `local f=obj.method` can move lookup outside the loop, but calls still need function/receiver moves and lose dynamic rebinding semantics. Measure main-position, colliding, and `__index`-table cases instead of claiming cached lookup universally wins. Userdata colon-call specialization is a reason not to rewrite it here; binder internals are outside this assignment. [lvmexecute.cpp:934–1008,1049–1057](../../luau/VM/src/lvmexecute.cpp#L934).

**Benchmark:** Same numeric work through visible local helper, parameter callback, table method, cached plain-table method, and small inline expression; 1/8/64 operation call sites and loop counts 1/100/10,000. Return/validate a dynamic checksum. Record emitted CALL count, total words, compile time, and execution counters. Include a helper too large to inline and an intentionally mutable method as correctness controls.

**Estimated patch size:** 40–100 lines of source-generation policy/example scaffolding plus 100–200 lines of tests; emitted size usually decreases for tiny helpers but can grow proportional to call-site count for larger inlined bodies. A full frontend implementation is not included in this estimate.

**Risks/confidence:** Low upstream risk; rerun opcode expectations after rebases because heuristics change. Medium correctness risk around multret/varargs, side-effect order, closure identity/captured mutation, and late-bound methods. High confidence for the demonstrated tiny helper; medium for generalized kernel fusion.

### Candidate 3 — Select loops by semantics, not “numeric is always faster”

**Current behavior/evidence:** Numeric `for` uses FORNPREP (including numeric validation/conversion) and FORNLOOP (increment/sign/limit test and backedge checks). Direct table iteration sets an internal traversal cursor; FORGLOOP traverses array then hash without a user iterator call. Recognized pairs/ipairs use specialized preparation, under safeenv; generic iterators still call through `luaD_performcally`. Ipairs terminates at the first nil, direct iteration skips nil slots and can visit hash fields. [Compiler.cpp:4330–4388,4397–4467](../../luau/Compiler/src/Compiler.cpp#L4330), [lvmexecute.cpp:2525–2850](../../luau/VM/src/lvmexecute.cpp#L2525).

**Smallest proposed change:** Emit numeric `for i=lo,hi,step` for a known counted range instead of a manually incremented while-loop. Emit `for k,v in t do` for all-elements iteration of a proven plain table, without wrapping it in a generated iterator function. Keep ipairs when first-hole termination is intended, and preserve custom/legacy iteration contracts. For a dense array sum, benchmark numeric indexing against generalized iteration: the latter supplies `v` without a separate GETTABLE.

**Instruction/branch/load argument:** Measured bytecode shape, not timing: the counted sum's steady body is `GETTABLE; ADD; FORNLOOP` (3 opcodes, 3 words) versus while-loop `JUMPIFNOTLE; GETTABLE; ADD; ADDK; JUMPBACK` (5 opcodes, 6 words). Initialization makes the complete toy functions equal in instruction-word size, so this is a dynamic-dispatch reduction, not a blanket total-bytecode-size claim. Generalized sum has `ADD; FORGLOOP` (2 opcodes, 3 words) but FORGLOOP has more internal traversal logic. Pairs/ipairs have a setup GETIMPORT/CALL, not necessarily a function call per element. [lvmexecute.cpp:2700–2804](../../luau/VM/src/lvmexecute.cpp#L2700).

**Benchmark:** Empty, 1, 16, 1,024, and 100,000-element dense arrays; holes at beginning/middle/end; mixed array/hash tables; tiny bodies versus more substantial arithmetic. Include an oversized/sparsely populated table to expose capacity scanning, and one `__iter` or legacy compatibility wrapper. Measure cycles/element and total visits separately, because different iteration semantics cannot be compared as equal work.

**Estimated patch size:** 30–80 lines of emitter rules/examples and 100–180 lines of tests. Counted-loop lowering removes two dynamic opcode executions per successful toy iteration without a VM binary change; whole-function bytecode savings depend on setup.

**Risks/confidence:** Low upstream risk; high correctness risk for an indiscriminate rewrite: changing mutation behavior, numeric conversion, nil handling, evaluation of bounds, floating steps/NaN, or custom iterator side effects changes programs. High confidence for a semantically proven counted loop; no confidence in a universal numeric-over-generalized claim.

### Candidate 4 — Emit stable literal schemas and constant keys for private hot records

**Current behavior/evidence:** Literal record constructors can use DUPTABLE; eligible constant fields need no SETTABLEKS afterward. Array literals reserve their array and use SETLIST batches. The compiler also predicts shapes for initially empty tables, so incremental construction is not automatically repeated rehashing. Small constant string keys (including a folded `t["field"]`) use GETTABLEKS; arbitrary string-key variables use GETTABLE. [Compiler.cpp:2704–2860,5729–5730](../../luau/Compiler/src/Compiler.cpp#L2704), [lvmexecute.cpp:511–557,764–850,2461–2522](../../luau/VM/src/lvmexecute.cpp#L511).

**Smallest proposed change:** Construct generated private records using one consistent literal schema; emit literal keys for schema-known access; hoist repeated invariant field reads to a local only across regions proven not to mutate/alias them. Keep dense array data separate from unrelated hash metadata if the schema naturally allows it. Consider fixed numeric tuple fields 1–256 only for private, demonstrably hot records after a benchmark; do not replace readable public object APIs wholesale.

**Instruction/branch/load/size argument:** Tested `{x=x,y=y,kind=1}` produces `DUPTABLE; SETTABLEKS; SETTABLEKS; RETURN` (6 words). The equivalent explicit assignments produce `NEWTABLE; SETTABLEKS; SETTABLEKS; LOADN; SETTABLEKS; RETURN` (10 words): 16 fewer instruction bytes, excluding the different constant/template payloads. The incremental form was **already pre-sized to hash capacity 4**, so claiming three rehashes would be false. DUPTABLE still clones a table, not a free shared immutable object. A constant numeric field read uses one word versus GETTABLEKS's two, and avoids a string-node probe, but tuple construction and data layout may offset that. [lvmexecute.cpp:2475–2485](../../luau/VM/src/lvmexecute.cpp#L2475).

**Cache implications:** Same schema/insertion order reduces slot churn, not all misses. One instruction's prediction can oscillate across heterogeneous layouts; resizing/collisions can move keys. The 8-bit slot hint is not an unlimited cache for arbitrary large records. Lookup caching does not make repeated `t.field` cheaper than a valid already-loaded local. Generalized traversal scans capacity, including holes/empty hash nodes, so avoid gross over-reservation when all-element iteration is frequent. [lvmexecute.cpp:525–555,2732–2770](../../luau/VM/src/lvmexecute.cpp#L525).

**Benchmark:** Records with 2/8/32 fields; access-only passes with construction outside timing, then construction separately. Compare homogeneous schemas, interleaved key orders, collision-heavy keys, post-resize records, nil fields, metatable and no-metatable variants. Include 256/512+ hash slots as a stress case, not as an assumed common workload. Record complete bytecode/constants size and allocated bytes, not just opcode text.

**Estimated patch size:** 40–100 lines of construction/access examples or emitter rules plus 100–200 lines of tests. The 16-byte reduction above is observed instruction storage for the tiny function only; total module/template memory can move differently.

**Risks/confidence:** Low upstream risk for source changes. Medium correctness risk for hoisting mutable reads, reordering effectful constructor expressions, changing hash iteration order, tuple field identity, or nil/sentinel conventions. High confidence in static key/literal paths; medium confidence in any workload gain from schema normalization, lower for tuple conversion without profiling.

### Candidate 5 — Opt in selected typed numeric kernels to native execution, and verify it happened

**Current behavior/evidence:** Native mode is disabled unless requested, and only some loading APIs apply it. Native-enabled plans already request type info; `--!native` also forces upstream O2/type-info 1. The generator exposes status, functions compiled/bound, native-code size, IR/assembly output, and optional execution counters. [native_code/mod.rs:102–159,363–483](../../src/native_code/mod.rs#L102), [source.rs:256–269](../../src/source.rs#L256), [Compiler.cpp:5626–5663](../../luau/Compiler/src/Compiler.cpp#L5626).

**Smallest proposed change:** Mark an isolated engine numeric kernel module `--!native`, annotate known scalar arguments accurately, retain an interpreter fallback, and select `Annotated` through the engine profile. Use the policy-aware load path and inspect status/bound function counts rather than trusting a Cargo feature or an annotation. Prefer a small kernel module to blanket-native compilation of configuration/glue code. No changes to host lowering hooks are proposed here.

**Instruction/branch/load argument:** In the pinned CodeGen IR experiment below, untyped `x=x*y+1` has three CHECK_TAG operations in the loop's ordinary path and stores the intermediate R6 value/tag before the addition. The annotated version has three entry guards, **still one CHECK_TAG on x in the loop**, but no loop y/intermediate tag checks and no intermediate R6 stores. This removes IR work and interpreter dispatch, not every guard. Numeric `for` backedge/interrupt checks remain. This is IR evidence, not a retired-instruction count or timing result.

**Benchmark:** Same kernel interpreted, native-untyped, native-typed; input lengths 0/1/32/1,024/100,000 and varying call counts. Separate cold native compilation from steady execution; verify checksum and fallback behavior for out-of-contract values. Report native code/data footprint, compilation failures, VM exits, and runtime budget use. Use x86-64 and AArch64 targets relevant to the engine; the local experiment only inspected host x86-64 IR.

**Estimated patch size:** 20–60 lines of host/kernel profile and 100–200 lines of measurement/correctness fixtures. Bytecode types and generated native code add storage; no numerical native-size saving is asserted. Existing 32 MiB budget is a constraint, not permission to compile all scripts.

**Risks/confidence:** Low VM-rebase risk because no fork; medium API/portability and code-size risk (native unsupported on some targets; build rejects Emscripten+jit). Type annotations must describe the intended contract, with interpreter correctness preserved. High confidence in the demonstrated IR simplification; medium confidence in net benefit after setup/footprint. [build.rs:178–189](../../build.rs#L178), [native_code/mod.rs:305–310,365–376](../../src/native_code/mod.rs#L305).

### Inferences

For an engine where generated Luau is the primary execution language, optimize at the source representation boundary: remove artificial per-element callbacks, expose arithmetic/local helpers, and retain a clean immutable runtime environment. These remove whole operations rather than shaving a branch from a VM operation. Keep plain table schemas deliberate, but do not invent a custom object layout without profiling. Numerical gains are deliberately not estimated from opcode counts.

### Gaps

None of these candidates has an engine workload A/B timing. Estimated patch sizes describe small policies/fixtures, not a whole new frontend. Native assembly size and cross-architecture throughput remain to be measured. Script identity, environment mutation, and iterator contracts must be agreed before transformations are enabled.

## 3. What was inspected experimentally, what baseline is feasible, and what is not worth patching yet?

### Takeaway

Reproducible pinned-compiler disassembly and CodeGen IR inspection are feasible now, without touching production code. A meaningful next patch is an engine-source-shape benchmark/golden fixture suite, not a VM dispatch rewrite. No timing benchmark was run during this research.

### Cited findings and experiment record

**Tooling observed:** Installed `luau` and `luau-compile` are present, but their provenance was not established, so they were not used for evidence. ### Benchmark recommendations / next patch

1. Add a small **generated-source-shape** fixture/benchmark suite first, independent of any future frontend. Compile with the actual runtime options and frozen L3i flag policy; preserve source plus normalized bytecode/IR expectations. Avoid fragile register-number goldens when an opcode property suffices. This makes upstream rebase changes visible without a VM fork.
2. Establish an interpreter baseline using the engine's safe-before-load environment and a policy-aware loader. Separately retain an unsafe control and native typed/untyped configurations. Assert correct results and verify native status when that is the tested mode.
3. Move runtime construction, source formatting, compilation, loading, input table construction, and warm-up **outside** the timed invocation loop. The existing `hot_paths` benchmark already compiles its loop functions outside Criterion iterations, but focuses on Luau-to-Rust dispatch and generally hand-assembled runtime setup; it does not establish these generated-Luau optimizations. [benches/hot_paths.rs:113–193](../../benches/hot_paths.rs#L113).
4. Measure dynamic inputs/checksums, tiny/large/pathological cases from each candidate, instructions/cycles/branches/misses when available, whole bytecode/constants size, and native-code footprint. Include a separate cold compile/load benchmark and a representative multi-kernel frame workload. Do not subtract a large “empty loop” baseline and present the noisy residue as authoritative.
5. If hardware counters are unavailable, record that limitation and use repeated wall-clock measurements; never report zero counters as improvement. Existing syscall-based infrastructure can be reused without requiring a `perf` executable. Keep counters/profiling/coverage off in shipping-throughput runs and use separate diagnostic runs for instrumentation.

### Areas examined with no promising patch at present

- **Interpreter dispatch/superinstructions:** Computed goto is already selected by the required compiler. No evidence justifies adding opcode fusion or rewriting the dispatcher before source-level removal is measured. Would increase bytecode/VM compatibility and rebase burden.
- **Blanket optimization/debug/type flags:** O2 and coverage-off already hold. Debug1 is useful for engine backtraces; changing to debug0 is primarily a size question, not demonstrated hot-loop improvement. Type1 without native execution is not a general interpreter accelerator.
- **Automatic loop unrolling/manual inlining everywhere:** Upstream O2 already has cost-limited versions. Excessive generated expansion can raise register/constant pressure and I-cache/code-size costs. [Compiler.cpp:950–1029,4190–4241,4330–4334](../../luau/Compiler/src/Compiler.cpp#L950).
- **Replace every pairs/ipairs with numeric for:** Already-specialized traversal and incompatible nil/metamethod semantics defeat this blanket recommendation. Direct traversal can require fewer dispatched opcodes than indexed numeric traversal.
- **Replace every colon call with a cached lookup:** NAMECALL receiver copying, CALL fallthrough, table main-position versus predicted-slot behavior, and non-table `__namecall` semantics make this workload-dependent. Only immutable plain-table cases warrant an A/B test.
- **Change hash algorithm or emulate hidden classes:** Existing string identity and per-site slot prediction already avoid many full lookups. Stabilize source schemas and measure polymorphism first. No claim that Rust HashMap/BTreeMap choice improves Luau table lookup.
- **Closure caching rewrite:** Upstream already emits DUPCLOSURE when eligible. Prefer making local helpers visible and captures immutable where semantics permit; no GC/instantiation patch is proposed.
- **New compiler-known-library infrastructure:** L3i already exposes callbacks and automatically supplies frozen compatibility-global modules. Start with fixtures for actual engine constants; no measured case yet warrants duplicating metadata or expanding the compatibility-global namespace purely for speed. [source.rs:30–62](../../src/source.rs#L30), [extension/install.rs:604–624](../../src/extension/install.rs#L604).
- **Filesystem/archive/database optimizations, Rust allocation/lock micro-tuning:** No such scans are part of the examined interpreter execution path. Rust binder/cache internals are assigned elsewhere; no speculative String/PathBuf/HashMap patch is bundled into this report.
