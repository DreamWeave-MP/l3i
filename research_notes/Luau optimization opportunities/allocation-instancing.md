# GC/allocation and script/module instantiation opportunities for a host runtime

## Performance Summary

- **Hot-path risk: medium**, potentially high during mass instantiation/save restoration or a high-frequency yield protocol. This is source research, not measured performance. No production changes, cargo benchmarks, or new benchmark results.
- Snapshot: L3i `62b894e3180baeb7bdced72afb4c99a6676951a4`; submodule Luau **0.740**, `c0e346edd89066b44dca174c9f54ce84c746a540`. PLAN.md was reported absent and was not used. Read the requested researcher guidance before source inspection.
- Host workload assumptions, **not observed facts**: a primary-runtime engine may instantiate many scripted entities, restore many instances from saves, execute stateful modules, and resume scheduled tasks frequently. Actual host call sites, object counts, save format, scheduler and allocation traces were not supplied. Rankings below are conditional on those shapes; no claim that a host currently recompiles every instance.
- Prioritize removing objects and temporary ownership before tuning GC. Four ranked candidates: **(1) share the frozen environment metatable; (2) avoid package-factory multi-result ownership; (3) use shared behavior plus explicit per-instance state where semantics allow; (4) offer borrowed coroutine-result consumption.** The first two are concrete L3i implementation opportunities; the third is an opt-in host code-shape choice; the fourth needs scheduler evidence.
- All byte estimates below are requested/logical payload formulas, not measured RSS or speedups. Allocator size classes, table capacities, feature flags, registry growth, and target layout affect physical memory. Estimated patch sizes are engineering estimates including focused tests, excluding comprehensive benchmark infrastructure.

## Likely Hot Paths

### Existing compile-once/load-once machinery — do not reinvent it

1. `Sandbox::load_template_in` compiles source, loads once on a dedicated loader thread whose globals are the frozen safe base environment, optionally compiles native code, and pins the template closure. `Sandbox::instantiate_in` subsequently calls `lua_clonefunction`, sets the requested environment and pins the clone; it does **not** compile, deserialize bytecode, hash bytecode, or compile native code again. [Sources: src/sandbox.rs:273–292, 391–483](../../src/sandbox.rs#L273).
2. Luau's clone allocates one Lua closure and copies its upvalue references, **sharing `cl->l.p`**, not deep-copying the prototype or captured mutable state. The loaded main closure has zero upvalues. Thus ordinary template instantiation is already constant-size with respect to bytecode length, apart from possible GC/stack/registry work. Do not generalize this to “cloning arbitrary closures isolates their state.” [Sources: luau/VM/src/lapi.cpp:2115–2127](../../luau/VM/src/lapi.cpp#L2115); [luau/VM/src/lvmload.cpp:822](../../luau/VM/src/lvmload.cpp#L822).
3. Repeated `LoadScope::load_source` recompiles; repeated `load_bytecode` avoids compilation but still reloads the VM object graph. A bytecode cache is not a loaded-prototype cache: the loader allocates Protos, instruction arrays, TValue constant arrays, nested-proto arrays, optional type/debug data, table constants and preload closures. A host should retain existing `Template`s per VM/base-environment generation if it is currently reloading the same script. There is no demonstrated need for a new VM deduplication scheme. [Sources: src/source.rs:245–269](../../src/source.rs#L245); [luau/VM/src/lvmload.cpp:412–624, 711–822](../../luau/VM/src/lvmload.cpp#L412).
4. `Sandbox::run` clones anew and collects all chunk results on every invocation. Appropriate for initialization, not automatically the right per-frame callback API: retain returned callbacks and use fixed-result/borrowed calls for updates rather than re-running module initialization. This is an integration recommendation, not a demonstrated host bug. [Sources: src/sandbox.rs:486–498](../../src/sandbox.rs#L486); [src/call.rs:250–309](../../src/call.rs#L250).
5. Luau already optimizes eligible nested closures with `DUPCLOSURE`: reuse requires compatible environment and captured values. An environment mismatch allocates a fresh closure; changed captures can trigger a lazy clone. Prototype sharing therefore does not eliminate all per-instance nested-function allocations. [Source: luau/VM/src/lvmexecute.cpp:2907–2962](../../luau/VM/src/lvmexecute.cpp#L2907).

### Native-code ownership and retained memory

- With `jit`, L3i hashes bytecode, retains one bytecode copy per module ID for collision checking, remembers allocation failures, and invokes the native compiler/binder. These costs occur on native compilation requests, not template clones. Do not replace the full-byte equality check with hash-only trust. Repeated fresh loads can still repeat hashing and comparisons even if native code can be reused. [Source: src/native_code/mod.rs:365–437](../../src/native_code/mod.rs#L365).
- Native execution metadata is attached to **Proto**, not independently owned by each closure. Binding sets `execdata`, `exectarget`, and `codeentry`; shared-context binding references existing module data and adds module references for bound protos. Proto destruction calls the execution destroy hook. Closure clones sharing a Proto naturally share that attachment. Never memcpy/cross-VM-transplant Protos or separately free native attachments from a clone. [Sources: luau/CodeGen/src/CodeGenContext.cpp:113–149, 263–271, 320–322, 375–378](../../luau/CodeGen/src/CodeGenContext.cpp#L113); [luau/VM/src/lfunc.cpp:184–185](../../luau/VM/src/lfunc.cpp#L184).
- Native module release/deallocation is refcounted; do not equate dropping one `Template` with immediately reclaiming its native code while clones/returned functions remain live. Counter recording deliberately roots a closure for readable counters. Rust's bytecode identity map also retains bytes independently of Lua heap accounting. Measure native and Rust memory separately from `lua_totalbytes`. [Sources: luau/CodeGen/src/SharedCodeAllocator.cpp:137–174, 274–296](../../luau/CodeGen/src/SharedCodeAllocator.cpp#L137); [src/native_code/mod.rs:270, 389, 435–437, 537–553](../../src/native_code/mod.rs#L435).

### Save/restore and import isolation: correctness gate before sharing more

- Templates resolve imports against the **loader's base environment**. `GETIMPORT` uses a non-nil cached constant when the executing closure's environment is safe. Changing the clone's environment does not rebuild its shared constant array. Safe is a compiler/VM contract, not a claim that all writes/shadows will dynamically invalidate imports. [Sources: src/sandbox.rs:273–277, 363–364, 473–479](../../src/sandbox.rs#L273); [luau/VM/src/lvmload.cpp:180–218](../../luau/VM/src/lvmload.cpp#L180); [luau/VM/src/lvmexecute.cpp:496](../../luau/VM/src/lvmexecute.cpp#L496).
- **Required tests/inference:** restore two instances with conflicting globals and package states; test `math.abs` or another cached base import shadowed in only one instance, nested callbacks, globals assigned by a first run then observed by a second, and a changed base/API version. `mutable_globals` is an existing compile-policy mechanism to investigate for intentionally mutable names; otherwise choose an appropriately unsafe environment/load policy. Do not silently accept cached base values when a host expects restored overrides. [Compile-policy source: src/source.rs:27, 196](../../src/source.rs#L196).
- Save application data, script identity/version and explicit package state; reconstruct fresh environments, `loaded` tables and stateful factory products. Do not serialize raw Proto/native pointers, VM registry refs, or assume a closure clone reconstructs mutable captures. Host-defined immutable packages may be shared intentionally; writable package objects/factory results must retain their isolation contract. [Existing construction: src/sandbox.rs:139–156, 325–368](../../src/sandbox.rs#L139).
- Sandbox `require` caches results per instance in `loaded`. The separate upstream require API uses host cache keys and runtime cache-management APIs. Do not collapse these namespaces into one global module-result cache when environments contain per-instance capabilities or save state. A source/template cache and a module-result cache have different validity rules. Cache key design should include the necessary script generation, compile policy/API layout and environment domain; bytecode persistence must respect the Luau pin and flag policy. [Sources: src/sandbox.rs:50–59](../../src/sandbox.rs#L50); [src/require.rs:73–94, 382–405](../../src/require.rs#L73); [src/flags.rs:1–5, 78–95](../../src/flags.rs#L78).

## Allocation / Clone Issues

### Rank 1 — Share the immutable environment metatable within a Sandbox

- **Exact site/current behavior:** `src/sandbox.rs:374–387` creates a fresh table with two hash slots, writes identical `__index = base_env` and `__metatable = false`, freezes it, and attaches it for **every** instance. The mutable environment and `loaded` table are separately allocated at lines 375 and 341. [Source](../../src/sandbox.rs#L374).
- **Why a host could stress it:** entity/script spawning and save restoration multiply this identical scaffolding by instance count, even when templates are already shared.
- **Minimal change:** construct and pin one protected, frozen metatable per Sandbox, then attach that table to each fresh environment. Keep environment, `_G`, print closure, require closure and `loaded` table per instance. Do not cache a mutable environment.
- **Structural impact:** for N simultaneous instances, replace N metatable headers and N two-slot hash parts with one of each plus one persistent registry pin. Baseline requested saving is approximately `(N-1) * (sizeof(LuaTable) + 2*sizeof(LuaNode))`, excluding any flag-dependent frozen-metamethod cache. Remove two metatable field insertions and their key hashing/lookups plus freeze setup per later instance; retain the setmetatable/barrier operation. Luau table creation allocates the header and hash storage separately. Frozen-meta butterfly, when active, adds its own array/cache allocation, making that another shareable cost; do not assume it is active from the release number alone. [Sources: luau/VM/src/ltable.cpp:961–978, 1576–1625](../../luau/VM/src/ltable.cpp#L961); [src/flags.rs:15–52](../../src/flags.rs#L15).
- **Benchmark/falsifier:** new_instance only, then complete instantiate+initialize, N=1/100/10,000, package counts 0/16/128; retain all instances for a heap comparison then drop/collect. Expect N-1 fewer metatable objects. Reject if that count does not fall or host metatable mutation/identity expectations make sharing observable. Timings may be dominated by factory bodies even if memory savings are real.
- **Size:** ~40–90 lines including tests. **Rebase/upstream:** low, binder-only, no Luau patch. **Semantic risk:** low-to-medium: script `getmetatable` sees false, but privileged host APIs can inspect/unfreeze/mutate metatables; document shared ownership and test independent globals. **Portability:** low; use public VM APIs, do not hard-code sizeof values. **Confidence:** high structural saving, unmeasured end-to-end benefit.

### Rank 2 — Consume only the needed package-factory result without temporary pins

- **Exact site/current behavior:** `src/sandbox.rs:342–349` clones a package Value into a Function, invokes with `LUA_MULTRET`, allocates a result Vec and pins every result, then uses only the first. `Value::clone` is another registry pin, **not** a deep clone or necessarily a fresh heap allocation. [Sources: src/sandbox.rs:342–349](../../src/sandbox.rs#L342); [src/value.rs:242–253](../../src/value.rs#L242); [src/call.rs:295–309](../../src/call.rs#L295).
- **Why a host could stress it:** per-instance package factories, particularly large extension sets or repeated save/import restoration. The Lua factory's own returned tables/closures are a separate cost that this patch does not remove.
- **Minimal change:** add an internal borrowed multi-result visitor with actual result count and existing 256-result limit, and invoke a borrowed function view or borrowed validated Value. Assign result slot 1 into `loaded` while the call frame remains live, without Vec ownership or per-result registry pins. Preserve current pinned-call error wording if this is a drop-in implementation change.
- **Important semantic trap:** blindly switching to existing `invoke_with`/one-result calls pads no-result factories with nil. Today **zero results do not overwrite an existing common package**, while an explicit nil first result removes it; a per-instance override can expose this distinction. Existing calls also reject >256 results. Preserve both or explicitly version the contract. [Sources: src/sandbox.rs:345–358](../../src/sandbox.rs#L345); [src/call.rs:279–309](../../src/call.rs#L279).
- **Structural impact:** per factory returning k>0 values, eliminate one Rust Vec allocation of capacity k (`k*sizeof(Value)` logical storage), k result pin/unpin pairs and the temporary factory pin/unpin. Registry capacity may already be available, so do not label each eliminated pin a heap allocation. Still run the factory and produce its results; no reduction claimed for its own userdata/tables. Also move `format!("Package {name}")` at sandbox.rs:331 to the error path: today every valid explicit package eagerly constructs an error-context String. [Source](../../src/sandbox.rs#L325).
- **Benchmark/falsifier:** 0/1/16/128 factories; each returns 0, nil, 1, 8, 256, or 257 values, including an override collision. Measure Rust allocs and registry growth independently of VM allocation volume. Reject if semantics differ or meaningful real-world factory counts make savings negligible; heavy factories may swamp pin cost.
- **Size:** ~100–180 lines with edge-case tests. **Rebase/upstream:** low-to-medium local call API work, no VM fork. **Semantic risk:** medium (zero-vs-nil, error text, arity limit, child-frame borrowing). **Portability:** low; public APIs and existing frame discipline. **Confidence:** high avoidable work, medium measured relevance.

### Rank 3 — Opt-in shared behavior with explicit state, not per-entity method closures

- **Exact mechanism:** existing template clones share Protos, but nested `DUPCLOSURE` falls back on environment mismatch at `luau/VM/src/lvmexecute.cpp:2917–2920` and changed captures at 2936–2952. Factories also intentionally execute once per instance at `src/sandbox.rs:342–358`. [VM source](../../luau/VM/src/lvmexecute.cpp#L2917); [factory source](../../src/sandbox.rs#L342).
- **Why a host could stress it:** many entities using identical update/event methods but capturing distinct `self`, state or hidden capabilities. This is a workload hypothesis; no host script sample was available.
- **Minimal change:** demonstrate one host-authored module that creates shared immutable behavior once and uses `update(state, dt)` rather than allocating per-entity method wrappers. Keep mutable state and capabilities explicit per instance. Use existing Templates for initialization; do not add a Proto cache or alter DUPCLOSURE. Pre-size known state arrays/tables through existing APIs and prefer borrowed strings/views at synchronous native boundaries.
- **Structural impact:** where m distinct method closures truly exist per entity, N entities can avoid up to `(N-1)*m` closures, with logical size `sum(sizeLclosure(upvalue_count))`; independently allocated upvalues may also disappear, but captured-by-value references are already inline and must not be counted as separate UpVal objects. Still allocate required state tables and retain shared behavior. No claimed instruction/branch reduction: explicit state arguments/table reads may increase call cost. If Luau already reuses the closure, there is nothing to save. [Allocation source: luau/VM/src/lfunc.cpp:67–80](../../luau/VM/src/lfunc.cpp#L67).
- **Benchmark/falsifier:** N=1/1,000/10,000, m=0/1/8/32; no captures, immutable captures, mutable captures and distinct environments. Measure construction allocations, retained closure/upvalue counts, update-loop cost and full-GC live traversal. Falsify if current code already shares closures or added state accesses outweigh memory benefit. Run interpreter and native modes separately.
- **Size:** ~100–250 lines for a representative example and benchmark/test fixture; migration size unknown without host source. **Rebase/upstream:** none for VM. **Semantic risk:** medium-to-high: implicit global environment/capability access, function identity and save state must not leak between entities; only opt in for functions designed for explicit state. **Portability:** low VM risk; packed/vector representations must still honor numerical semantics. **Confidence:** high mechanism, medium-to-low host payoff until real scripts are inspected.

### Rank 4 — Borrow coroutine yield/return results for immediate scheduler consumption

- **Exact site/current behavior:** `Thread::collect`, `src/thread.rs:181–195`, allocates a Vec for nonzero result counts, pins every result, clears the coroutine stack and returns owned results on every successful resume/yield. Thread creation is separate and already exposed; reset exists. [Source](../../src/thread.rs#L181).
- **Why a host could stress it:** a primary scheduler frequently yielding a small opcode, delay, handle or event payload. This is conditional: no benefit for zero-result yields, and owned values remain necessary when the scheduler retains them.
- **Minimal change:** add an opt-in visitor/fixed-result resume API that reads results synchronously under a frame/root lease and pops them afterward; keep existing owned API. Do not let borrowed views escape or allow resume/reentrant mutation of that thread during consumption. Implement only after a scheduler trace shows immediate consumption.
- **Structural impact:** avoid one Rust Vec allocation for k>0 and k pin/unpin pairs per consumed yield. No claim of eliminating a coroutine, its stacks, or Lua-side yield payload objects. This reduces host allocation/registry churn rather than inherently large Lua GC volume.
- **Benchmark/falsifier:** 1/100/1,000 coroutines, 10,000 aggregate resumes; 0/1/4/32 results, numeric and table/string payloads, immediate vs retained results, error and break paths. Measure allocations/resume and p50/p99 scheduler-batch latency. Reject if the host only uses zero results or always retains results, or if visitor bookkeeping loses the benefit.
- **Size:** ~120–250 lines plus scheduler adoption. **Rebase/upstream:** medium binder API effort, no Luau fork. **Semantic risk:** medium-to-high (lifetime, stack cleanup, errors, reentrancy). **Portability:** low. **Confidence:** high current ownership cost, medium-to-low workload priority.

## Algorithmic / IO Issues

### Allocation and GC baseline already optimized

- Luau 0.740 uses incremental, non-generational, non-moving mark/sweep with GC assists and an indivisible atomic phase; pacing exposes goal, step size and multiplier. Reducing live scaffolding can reduce traversal as well as allocation pressure; merely shifting assists does not remove collector work. [Source: luau/VM/src/lgc.cpp:28–45, 75–115](../../luau/VM/src/lgc.cpp#L28).
- Small allocations already use size classes and page allocation; logical object allocations do not imply calls to system malloc. Runtime creation currently uses `luaL_newstate` with its default allocator; `onallocate` is observation, not allocator replacement. Buffer cage support is buffer-specific, not a universal heap allocator. [Sources: luau/VM/src/lmem.cpp:554–704](../../luau/VM/src/lmem.cpp#L554); [src/runtime/mod.rs:138–176](../../src/runtime/mod.rs#L138); [src/memory.rs:181–200](../../src/memory.rs#L181).
- Allocation observation is already installed **only when profiling is enabled**. It charges positive growth to the innermost active call using a RefCell borrow and addition, not a HashMap lookup per allocation. Context hashing occurs when scope totals are committed. No mutex contention was found in this examined path. Disabled profiler/limits already make call scopes a no-op. [Sources: src/runtime/mod.rs:175–177](../../src/runtime/mod.rs#L175); [src/runtime/shared.rs:470–471, 640–663](../../src/runtime/shared.rs#L640); [src/runtime/call_scope.rs:63–87, 136–141](../../src/runtime/call_scope.rs#L63).
- Strings already intern in the VM: repeated identical pushes hash/search but do not necessarily allocate new strings. Borrowed `&str`/`&[u8]` conversion exists, while String/Vec conversions copy. Prefer borrowing when values are consumed synchronously, not another blanket string-intern layer. Buffer-building paths may allocate before final intern lookup, so retained string count alone is not allocation volume. [Sources: luau/VM/src/lstring.cpp:71–160](../../luau/VM/src/lstring.cpp#L71); [src/convert/string.rs:6–20, 47–87](../../src/convert/string.rs#L6).
- Tagged userdata already allocate inline payloads with a registered metatable, rather than creating per-object metatables. Value-layout/vector/raw-argument fast paths exist. Do not replace owning userdata with light userdata without a new lifetime/identity contract. [Sources: src/userdata/tagged.rs:7–10](../../src/userdata/tagged.rs#L7); [csrc/extra.cpp:148–191](../../csrc/extra.cpp#L148).
- The loaded-package table is already pre-sized to common+explicit packages; environment capacity is already four fields. The BTreeMap holds common packages and is iterated during setup, not searched on every Lua require. Replacing it with HashMap has no demonstrated win and could change factory order. [Source: src/sandbox.rs:111, 341–358, 375](../../src/sandbox.rs#L341).
- Source compilation makes a Rust bytecode copy of the C compiler result before freeing it. This is real cold-path copy work, but existing template reuse amortizes it; changing bytecode buffer ownership is below the ranked instance costs absent reload traces. [Source: src/source.rs:215–226](../../src/source.rs#L215).
- `RequireNavigator` names/config return owned Strings and copy into caller buffers. These are plausible load-time host allocation costs, not evidence of repeated archive opens or filesystem scans: navigation and I/O are delegated to the host. Inspect the host's navigator hit/miss traces before redesigning names/cache normalization. No archive/database implementation was identified in the examined loading paths. [Source: src/require.rs:44–94, 125–140, 203–257](../../src/require.rs#L44).

### Rejected or deferred speculative changes

- **GC redesign/generational or moving GC, custom slab allocator, broad GC suppression:** invasive VM fork, pointer/FFI compatibility and upstream/rebase risk; existing pages and pacing already target allocation cost. First measure allocation sources and p99 assists. Manual stepping may schedule work but is not an allocation reduction. [Collector baseline](../../luau/VM/src/lgc.cpp#L28).
- **Global prototype/constant deduplication or cross-VM Proto sharing:** already shared within Templates; imported values, mutable VM caches, GC references and native attachments make unrestricted interning unsafe. Prototype table constants are templates, not permission to share all returned mutable tables. [Loader](../../luau/VM/src/lvmload.cpp#L494); [native binding](../../luau/CodeGen/src/CodeGenContext.cpp#L113).
- **Automatically pool all coroutines:** new thread needs a thread object plus initial CallInfo and TValue arrays. However reset closes upvalues, shrinks oversized stacks/CallInfo arrays, clears slots and finalizer state; it does not replace globals. Pooling can retain old environments/capabilities and does not automatically preserve large-stack capacity. Use bounded same-domain reuse only after measuring scheduler churn and defining finalizer/cancellation behavior. [Sources: luau/VM/src/lstate.cpp:28–40, 138–198](../../luau/VM/src/lstate.cpp#L138); [src/thread.rs:206–218](../../src/thread.rs#L206).
- **Global mutable-table pools or sharing all `loaded` tables:** clearing scans existing capacity and pools retain peak storage; aliasing and save isolation become harder. Share the immutable metatable first. [Clear implementation: luau/VM/src/ltable.cpp:1548–1573](../../luau/VM/src/ltable.cpp#L1548).
- **Delete profiler branches, hash-collision checks or eager factory side effects:** already optional instrumentation, security/identity checks and observable factory order are not free optimization targets. Even overridden common factories currently run; lazily skipping them is a semantic change. [Sources: src/native_code/mod.rs:378–390](../../src/native_code/mod.rs#L378); [src/sandbox.rs:354–358](../../src/sandbox.rs#L354).

## Benchmark Recommendations

### Existing coverage and interpretation traps

- `benches/hot_paths.rs:172–211` prepares functions outside timing and runs 1,000-call Lua loops; useful for steady boundary cost, not template-load or instance construction. It compares borrowed and pinned return paths. Its “value pin create and drop” at lines 291–292 actually creates a new Lua table too; add a preexisting-table pin-only control. [Source](../../benches/hot_paths.rs#L172).
- Native benchmark setup uses Sandbox/Templates (e.g. `benches/packed_quat.rs:110–167`, `benches/bytes.rs:62–105`) but is not an isolated mass-instantiation benchmark. Existing packed-quaternion cases explicitly compare allocating userdata operations; use them as a code-shape model, not proof of host savings. [Sources](../../benches/packed_quat.rs#L110); [bytes setup](../../benches/bytes.rs#L62).
- `benches/intern.rs:594–638` already separates stopped-GC first-pass heap growth, retained heap, duplicate passes, live GC and reclamation costs. Reuse that measurement discipline. Its stopped-GC heap delta is **net requested heap growth**, not an exact sum of allocation traffic: explicit frees/reallocations and Rust/native allocations can escape that metric. Counters/minima are useful diagnostics, not production tail-latency measurements. [Source](../../benches/intern.rs#L594).

### Measurements worth adding before implementation

1. **Compile/load/clone:** source sizes 1 KiB/32 KiB/512 KiB; nested prototypes 0/10/100; instances 1/100/10,000. Separate compile, bytecode load, clone into prebuilt env, environment creation, package factories, initializer execution, first call and steady calls. Compare one retained Template against repeated load_bytecode as a deliberately expensive baseline; do not advertise that delta as a new optimization of the already-cloned path.
2. **Allocation accounting:** record requested allocation calls/bytes by Luau object type and raw-array allocation, Rust allocation calls/bytes, peak heap and post-full-GC retained heap. Report per-instance/per-resume and amortized template cost. `Runtime::total_bytes_in`, total bytes, Count+CountRemainder, memory_dump/gc_dump, allocation_rate and profiler activity are available; allocation_rate is an estimate and returns -1 before enough history. [Sources: src/runtime/mod.rs:336–343, 427](../../src/runtime/mod.rs#L336); [src/memory.rs:18–85](../../src/memory.rs#L18).
3. **Correct telemetry interpretation:** the L3i comment at `src/runtime/shared.rs:641` says not every fixed GC allocation is reported, but this pin's `luaM_newgcofixed_` **does call onallocate** at `luau/VM/src/lmem.cpp:699–701`. Treat that comment as needing correction/verification, not a basis for claiming absent fixed-object events. The existing callback discards type/tag/category, ignores frees/shrinks and can skip attribution when its RefCell cannot be borrowed. It reports growth activity in active scopes, not ownership or a complete lifetime allocation log. Add typed counters in a separate diagnostic patch without double-installing callbacks. [Callback](../../src/runtime/shared.rs#L640); [fixed allocation](../../luau/VM/src/lmem.cpp#L681).
4. **Categories are attribution, not isolation:** call_scope sets the main thread's category only under profiling; the template loader is a distinct thread and new threads inherit the creator's active category at creation. Audit categories on actual allocating threads before using category totals as per-script ownership. Shared templates/metatables should usually be common overhead, not charged repeatedly to entities. [Sources: src/runtime/call_scope.rs:80–85](../../src/runtime/call_scope.rs#L80); [src/sandbox.rs:416–429](../../src/sandbox.rs#L416); [luau/VM/src/lstate.cpp:152–154](../../luau/VM/src/lstate.cpp#L152).
5. **Timing:** profiling off and on, limits off/on, default interpreter and explicit native modes. Warm and cold paths separately; run enough batches for collections with normal GC enabled and report p50/p95/p99, not just stopped-GC speed. Bound the live set between samples so a Criterion loop does not accidentally benchmark unbounded registry/table retention. Inspect object counts/heap graphs outside timed sections. Test x86-64 and AArch64 where the host ships; do not extrapolate instruction counts or object sizes across architectures.
6. **Pathological correctness controls:** factory 257-result limit; zero-return override versus explicit nil; source/base-generation invalidation; two instances with conflicting globals and cached imports; nested closures surviving original Template drop; native counter mode retention; error/yield/break/cancellation cleanup; save restore into a fresh VM.

## Suggested Next Patch

1. Add construction/clone/factory fixtures and allocation counters as a separate diagnostic change, starting with N-instance object-count slopes and import/save-isolation tests. Obtain a host trace to replace the workload assumptions.
2. Implement only the shared frozen environment metatable first; validate N-1 fewer metatable objects, independent env/loaded tables and allowed host metatable behavior. This is the smallest concrete production candidate, not permission to share mutable instance state.
3. Add a borrowed actual-count result visitor and apply it to package factories, preserving zero-vs-nil, result limits, error wording and factory ordering. Include the eager success-path diagnostic String cleanup.
4. Pilot explicit-state shared behavior in one real host module; pursue borrowed coroutine results only if scheduler traces show immediately consumed nonempty yields. Keep existing owned APIs for retention.
5. Revisit GC pacing only after allocation reductions and live-set measurements. No native ownership redesign, new cross-VM prototype cache, or collector fork is justified by this review.
